# The research corpus

This directory is the raw evidence base, published so the reasoning behind the
rules can be audited rather than taken on trust.

| file | what it is |
|---|---|
| `sources.yaml` | The full catalog — 82 source records with per-source notes or catalog metadata. The machine-readable master; rule citations resolve against it. |
| `research-report.md` | The synthesis: what the literature actually supports, where findings conflict, and which questions stayed open. |
| `evidence-matrix.md` | Rule × source cross-tabulation, generated by `render_rules.py`. Also lists sources no rule cites. |
| `research-limitations.md` | What the sweep could not establish, and why. Read this before quoting any figure from the corpus. |

## How the corpus was built

The original 42-record sweep was collected 2026-07-24 with live access. A
targeted nine-record v1.3 extension and 31 round-two publication records were
verified on 2026-07-25 against primary academic pages and official Anthropic
documentation. All 82 source records carry a versioned URL or
explicitly scoped living-page snapshot, section locator, verification date,
status, supersession field, and SHA-256 of the exact decompressed response bytes
observed during retrieval. Dynamic Anthropic HTML is marked as point-in-time
provenance because immediate refetches were not byte-identical.

The upstream round-two dossier referenced by historical `provenance` strings was
not shipped. Each round-two record therefore states that limitation, binds the
primary response independently, and defers rule-specific support detail to
`skill/rules/rules.yaml:source_claims`. Eight are retained as catalog-only
records and are not cited by a rule.

Six candidate sources and one dated provider price table, all arriving from a
second implementation of this skill, **could not be corroborated** and were
excluded outright. None is cited by any rule. An uncheckable citation is worse
than no citation, because it survives review.

## What the corpus does not do

It does not prove that this skill works. It establishes that the *mechanisms* the
rules use are real and measured by someone — compression ratios, cache pricing
behavior, context-position effects, injection vectors. Whether a given rule helps
on **your** target is an empirical question about your target, which is why the
skill ships a harness and an evaluation protocol instead of a table of promised
percentages.

Sources not cited by a rule are kept and reported rather than quietly dropped,
because a corpus trimmed to only what supports the conclusion is not a corpus.

## Reading a source type

Each record carries a `source_type`. The values present in the catalog, by count:

| type | n |
|---|---|
| `peer-reviewed-conference` | 24 |
| `provider-doc` | 12 |
| `preprint` | 11 |
| `peer-reviewed` | 10 |
| `conference-paper` | 7 |
| `paper` | 6 |
| `peer-reviewed-findings` | 4 |
| `engineering-report` | 3 |
| `peer-reviewed-journal` | 2 |
| `technical-report` | 1 |
| `arxiv-preprint` | 1 |
| `peer-reviewed-workshop` | 1 |

The type travels with the citation into [`../docs/RULES.md`](../docs/RULES.md), so a
rule resting on a vendor's own documentation is visibly distinguishable from one
resting on a replicated result. Several rules rest on the weaker types; that is
disclosed per rule rather than averaged away.

**A known data-quality flaw in this field, stated rather than cleaned up.** These
twelve values are not a single controlled vocabulary — `peer-reviewed` and
`peer-reviewed-journal` mean the same thing, as do `preprint` and `arxiv-preprint`,
and `paper` is ambiguous against `conference-paper`. The values were recorded
per-source during collection without a fixed enum, and normalizing them now would
mean re-deriving 82 judgments from titles rather than from the pages actually read.
Treat the type as a hint, and check the `url` when a distinction matters.
